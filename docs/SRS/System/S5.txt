\nsection{S.5 Prioritization}
%---------------------------------

This section classifies the requirements of S.2, the interfaces of S.3, the usage scenarios of S.4, and the safety and security requirements identified in the Hazard Analysis by their degree of criticality, using the MoSCoW method:

\begin{itemize}
    \item \textbf{Must have (M):} Essential for the system to meet its goals. The Toolbox cannot be released without it.
    \item \textbf{Should have (S):} Important, and planned for the capstone release, but the system can still meet its core goals without it.
    \item \textbf{Could have (C):} Desirable, and implemented if time allows. Otherwise left for future \term{software-subteam}{software subteams}.
    \item \textbf{Won't have (W):} Not planned for the current release.
\end{itemize}

The criteria used to assign each priority are explained in S.5.12, and the influence of security concerns in S.5.13. S.5.14 then uses these priorities to plan the order in which the requirements will be implemented.

\subsection*{S.5.12 Justification for Prioritization}
\addcontentsline{toc}{subsection}{S.5.12 Justification for Prioritization}

Priorities were assigned using four criteria, in the following order:

\begin{enumerate}
    \item \textbf{Dependency:} A requirement that other Must requirements depend on is itself a Must. For example, the Toolbox Broker's routing (\reqref{FR-BR-3}) and the Material Testing Manager's material properties (\reqref{FR-MT-4}) are Must because every service, and the \term{failure-load}{failure load} estimate, respectively, cannot work without them.
    \item \textbf{Project goals:} Requirements that directly deliver one of the goals in the Problem Statement, being information centralization, model analysis, material testing support, knowledge transfer, and maintainability by a \term{software-subteam}{software subteam}, were ranked above those that only improve them.
    \item \textbf{Member survey:} Between features that serve the same goal, the member survey (P.7.1) was used to rank them. \term{failure-load}{Failure load} prediction (feature E), the archive of \term{past-design}{past designs} (feature A), and the material test database (feature B) were the most highly rated, so their requirements are Must. Rule compliance (feature J) was rated lower, so the Rule Compliance System's functional requirements are Should.
    \item \textbf{Schedule and risk:} The Development Plan identifies \term{step}{STEP} model loading and visualization as the riskiest feature, and the focus of the Proof of Concept. Requirements on that path are Must, so that the riskiest work is done first, while requirements only needed after the first competition season, such as archiving \term{current-model}{current models} (\reqref{FR-MA-6}), are Should.
\end{enumerate}

Must requirements together form the minimum system that meets every project goal. Should requirements are planned for the capstone release, and Could requirements are left to future \term{software-subteam}{software subteams} if time does not allow. No requirement in S.2 is currently classified as Won't have. Features that were deliberately left out of S.2, such as onboarding material (survey feature H) and the identification of a bridge's weak points, are not part of this release, and the extensibility requirements (\reqref{NFR-BR-1}, \reqref{NFR-PA-3}) ensure they can be added later without changing existing services.

%=================================
\subsection*{S.5.13 Role of Security Concerns}
\addcontentsline{toc}{subsection}{S.5.13 Role of Security Concerns}

Security and safety concerns raised the priority of several requirements that would otherwise have been ranked lower. The club's teams compete against each other, so a leak of a team's \term{current-model}{current design} to another team would undermine trust in the Toolbox and make teams unwilling to store their work in it. For this reason, every requirement that enforces access control or team data isolation, being \reqref{FR-AC-1} to \reqref{FR-AC-6}, \reqref{FR-BR-2}, and SR-KR-3, is Must, as are encrypted communication (\reqref{NFR-WS-2}) and password hashing (\reqref{NFR-AC-1}), which protect members' credentials.

Safety concerns affected the analysis tools in the same way. Although the Toolbox does not control any physical equipment, a team that trusts an incorrect estimate or compliance result may build, or load test, a weaker bridge, or one that is disqualified. Requirements that prevent results from being over-trusted, being assumption disclosure (\reqref{FR-PA-4}), error reporting (SR-PA-1), and the absence of false passes (\reqref{NFR-RC-1}), are therefore Must, even where the feature they belong to is not. Finally, because the Knowledge Repository becomes the only copy of the club's history, the requirements that protect it from loss, being data durability (\reqref{NFR-KR-2}), external backups (SR-KR-1), and error reporting on storage (SR-KR-5), are Must.

\paragraph{Phase 1: Proof of Concept.} The Development Plan identifies loading a \term{step}{STEP} model, displaying it, and extracting its data as the riskiest part of the project, so it is implemented first. Demonstrating it at the Proof of Concept confirms that the Model Analysis System, on which both analysis subsystems depend, is feasible before the rest of the system is built around it. If the demonstration shows that this path is not feasible, the Development Plan's risk mitigation applies, and the scope of the analysis tools is revised before Revision 0.

\paragraph{Phase 2: Revision 0.} Revision 0 delivers the minimum system that meets every project goal: members can log in, store and search the club's information, analyse their team's model and estimate its \term{failure-load}{failure load}, record material tests, and write \term{exit-document}{exit documents}. The Web Server, Access Control System, Toolbox Broker, and Knowledge Repository are implemented first within this phase, since every other service depends on them (Table~\ref{tab:traceability}). All safety and security requirements classified as Must, such as team data isolation (\reqref{FR-AC-6}) and data durability (\reqref{NFR-KR-2}), are part of this phase, so that the system is secure from the first time members use it.

\paragraph{Phase 3: Revision 1.} The final phase adds the Rule Compliance System, which was ranked below the other analysis tools in the member survey, together with the Should requirements that improve the usability, performance, and maintainability of the services delivered at Revision 0. Feedback from the Revision 0 demonstration and from usability testing is also addressed in this phase. Because \reqref{NFR-RC-1} only applies once compliance checking exists, it is implemented together with the Rule Compliance System rather than at Revision 0.

\paragraph{After Revision 1.} The Could requirements are implemented if time allows before the final demonstrations. Otherwise, they are documented as future work for the club's \term{software-subteam}{software subteam}. The extensibility requirements (\reqref{NFR-BR-1}, \reqref{NFR-PA-3}) ensure that they, and features outside the current scope, can be added later without changing existing services.

The phasing of the safety and security requirements from the Hazard Analysis is given in the Hazard Analysis roadmap.
