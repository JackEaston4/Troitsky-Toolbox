\subsection{Tests for Functional Requirements} \label{SecFRTests}

The tests below are categorized by the components defined in Section S.2 of the
SRS \citep{TroitskySRS}, so that every functional requirement is covered. Each
test is a system-level test of the deployed system, following a workflow that a
club member performs through the Toolbox Web App, and verifies several related
requirements. The tests also verify the functional safety and security
requirements that the Hazard Analysis Roadmap \citep{TroitskyHazardAnalysis}
plans for the capstone. Together, they verify the model analysis correctness,
data integrity, and access control identified as primary objectives in the
Objectives section, while functional usability is assessed by the non-functional
tests and the winter usability report.

Inputs and expected outputs refer to the symbolic constants of
Table~\ref{TblSymbolicConstants} and the test data of Table~\ref{TblTestData}
(Symbolic Parameters appendix), shown in \textsc{small capitals}. Tests whose
outputs are numerical or follow from a formula are automated, so that they can be
repeated on every change; tests that depend on what a member sees on screen are
manual.

\subsubsection{Web Server (S.2.1)}

\begin{enumerate}

\item \testdef{T.FR.WS.1.1}\\
\textbf{Control:} Manual\\
\textbf{Initial State:} System deployed. User not logged in.\\
\textbf{Input:} User opens the public landing page, then attempts to open the
Knowledge Repository. User then logs in with valid credentials, opens the
Knowledge Repository, and logs out.\\
\textbf{Output:} The landing page is shown without logging in. The Knowledge
Repository redirects to the login page until the user logs in, and is no longer
accessible after logout.\\
\textbf{Derivation:} Verifies FR-WS-1, FR-WS-2, FR-WS-3.

\end{enumerate}

\subsubsection{Access Control System (S.2.2)}

\begin{enumerate}

\item \testdef{T.FR.AC.2.1}\\
\textbf{Control:} Manual\\
\textbf{Initial State:} An executive is logged in.\\
\textbf{Input:} The executive creates an account three times: with a password
one character shorter than \const{password\_min\_length}, with an entry from
\const{password\_blocklist}, and with a password consisting solely of lowercase letters and exactly \const{password\_max\_length} characters long. The executive then changes the
account's role and team, ends its session from the server side, and deactivates
it.\\
\textbf{Output:} The first two passwords are rejected, with a message stating
that the password is too short or too common. The third is accepted, since no
composition rules apply. The account always has exactly one role and at most one
team. Ending the session logs the user out, and the deactivated account cannot
log in.\\
\textbf{Derivation:} Verifies FR-AC-1, FR-AC-2, FR-AC-4, FR-AC-5, SR-AC-2,
SR-WS-5.

\item \testdef{T.FR.AC.2.2}\\
\textbf{Control:} Automatic\\
\textbf{Initial State:} One account for each role of FR-AC-2, on two different
teams. Each team has a current bridge model.\\
\textbf{Input:} A script requests, as each account, member management, team
assignment, rule configuration, season archiving, test result review, and each
team's current model.\\
\textbf{Output:} Member management, team assignment, and rule configuration are
allowed only for executives and maintainers; season archiving and test result
review only for executives; and a team's current model only for members of that
team. Every other request is refused with an error and changes nothing.\\
\textbf{Derivation:} Verifies FR-AC-3, FR-AC-6, FR-BR-2.

\end{enumerate}

\subsubsection{Toolbox Broker (S.2.3)}

\begin{enumerate}

\item \testdef{T.FR.BR.3.1}\\
\textbf{Control:} Manual\\
\textbf{Initial State:} System has just been started. User logged in.\\
\textbf{Input:} User opens each tool. The Material Testing Manager is then
stopped, and the user requests it, then searches the Knowledge Repository.\\
\textbf{Output:} Every tool opens. The request to the stopped service returns an
error message within \const{broker\_timeout} instead of hanging, and the search
returns its results.\\
\textbf{Derivation:} Verifies FR-BR-1, FR-BR-3, FR-BR-4.

\end{enumerate}

\subsubsection{Knowledge Repository (S.2.4)}

\begin{enumerate}

\item \testdef{T.FR.KR.4.1}\\
\textbf{Control:} Manual\\
\textbf{Initial State:} User logged in. Repository contains items with known
metadata.\\
\textbf{Input:} User uploads one file of each type in \const{common\_file\_types},
each with a title, a category from \const{category\_list}, a year, a team, and
tags. User then makes three uploads that each break one metadata rule: no title,
a category not in \const{category\_list}, and no year. Finally, the user searches
by keyword, filters by category, year, team, and tag, previews a file of each
type in \const{preview\_file\_types}, and downloads every uploaded file.\\
\textbf{Output:} Valid uploads are stored with their metadata. Each of the three
invalid uploads is rejected, with a message naming the field. Searches and
filters return exactly the items that match them, previews display in the
browser, and each downloaded file has the same SHA-256 hash as the uploaded
file.\\
\textbf{Derivation:} Verifies FR-KR-1, FR-KR-2, FR-KR-3, FR-KR-4, SR-KR-4.

\item \testdef{T.FR.KR.4.2}\\
\textbf{Control:} Manual\\
\textbf{Initial State:} A member has uploaded an item.\\
\textbf{Input:} The uploader edits the item, another member attempts to edit it,
and an executive archives it. The repository's database server is then stopped,
and a member uploads a file.\\
\textbf{Output:} Each change asks for confirmation first, and the other member's
edit is refused. The archived item no longer appears in search results but can
still be opened. The failed upload shows an error message, and the file is not
listed once the database is restarted.\\
\textbf{Derivation:} Verifies FR-KR-5, SR-KR-2, SR-KR-5.

\end{enumerate}

\subsubsection{Model Analysis System (S.2.5)}

\begin{enumerate}

\item \testdef{T.FR.MA.5.1}\\
\textbf{Control:} Manual\\
\textbf{Initial State:} Team member logged in. \const{mat\_set\_a} is stored.\\
\textbf{Input:} User uploads three invalid files: a PDF renamed with a
\texttt{.step} extension, a STEP file with a header but no geometry, and
\const{ref\_model} truncated to half its size. User then uploads
\const{ref\_model} with \const{mat\_set\_a} selected, confirms the import
summary, and rotates, zooms, and pans the 3D view. Finally, with
\const{ma\_timeout} set to \const{ma\_timeout\_test} in the test deployment, the
user uploads \const{ref\_model} again.\\
\textbf{Output:} Each invalid file is rejected, with a message stating that it is
not a STEP file or contains no readable geometry. Before any analysis, the import
summary shows the dimensions of \const{ref\_model} within
\const{dimension\_tolerance} and its mass within \const{calc\_tolerance} of the
values in Table~\ref{TblTestData}. The 3D view responds to each interaction and
matches the model in CAD. The last upload stops after \const{ma\_timeout\_test}
with a message that the time limit was exceeded, and no model is stored.\\
\textbf{Derivation:} Verifies FR-MA-1, FR-MA-2, FR-MA-3, SR-MA-1, SR-MA-3.

\item \testdef{T.FR.MA.5.2}\\
\textbf{Control:} Manual\\
\textbf{Initial State:} Two teams exist, with no current models.\\
\textbf{Input:} A team member uploads \const{ref\_model} as a current model. A
teammate, a member of the other team, and a former team member try to open it.
An executive then archives the season's models, and a general member browses
past designs.\\
\textbf{Output:} Only the teammate can open the current model. After archiving, it
becomes a past design recording its year and team, which every member can view
and filter but not modify.\\
\textbf{Derivation:} Verifies FR-MA-4, FR-MA-5, FR-MA-6, FR-AC-6.

\end{enumerate}

\subsubsection{Performance Analysis System (S.2.5.1)}

\begin{enumerate}

\item \testdef{T.FR.PA.6.1}\\
\textbf{Control:} Automatic (results) and Manual (displayed assumptions)\\
\textbf{Initial State:} \const{ref\_model}, \const{mat\_set\_a}, and
\const{mat\_set\_b} are stored.\\
\textbf{Input:} A performance analysis of \const{ref\_model} is run with
\const{mat\_set\_a}, then with \const{mat\_set\_b}, then with the calculation
library made to return a non-finite stress.\\
\textbf{Output:} For each material set, the failure load and load-to-mass ratio
are within \const{calc\_tolerance} of the expected values in
Table~\ref{TblTestData}, and the result names the material set used. The
assumptions and limitations are shown with the results. For the non-finite
stress, an error is shown instead of an estimate.\\
\textbf{Derivation:} Verifies FR-PA-1, FR-PA-2, FR-PA-3, FR-PA-4, FR-MT-4,
SR-PA-1. Expected values follow from SRS S.7.2, as derived in
Table~\ref{TblTestData}.

\end{enumerate}

\subsubsection{Rule Compliance System (S.2.5.2)}

\begin{enumerate}

\item \testdef{T.FR.RC.7.1}\\
\textbf{Control:} Manual (rule set editing) and Automatic (compliance checks)\\
\textbf{Initial State:} Executive logged in. The compliance models of
Table~\ref{TblComplianceModels} are stored.\\
\textbf{Input:} The executive imports \const{ruleset\_test}, adds a rule, edits
its limit, and removes it. A script then runs a compliance check of each
compliance model against \const{ruleset\_test}.\\
\textbf{Output:} The rule set is stored under its year, and after each edit lists
exactly the expected rules. \const{rc\_pass} and \const{rc\_limit} pass every
rule, and each other compliance model fails only the rule it is named for,
showing its measured value and the allowed range. The materials rule is listed
as a manual check for every model.\\
\textbf{Derivation:} Verifies FR-RC-1, FR-RC-2, FR-RC-3, FR-RC-4, FR-RC-5.
Expected results follow from the \texttt{RuleComplianceCheck} predicate of SRS
S.7.3, whose limits are inclusive.

\end{enumerate}

\subsubsection{Material Testing Manager (S.2.6)}

\begin{enumerate}

\item \testdef{T.FR.MT.8.1}\\
\textbf{Control:} Manual\\
\textbf{Initial State:} \const{mat\_set\_b} is stored as the previous year's
results.\\
\textbf{Input:} User enters the first specimen of \const{mat\_set\_a} through the
form, first without a grain orientation, then with it. User imports the remaining
specimens of \const{mat\_set\_a} from \const{mt\_import\_file}, which also

the strength of \const{mat\_set\_a} is recomputed to the flagged value in
Table~\ref{TblTestData}, and the flagged specimen remains stored, marked
invalid.\\
\textbf{Derivation:} Verifies FR-MT-1, FR-MT-2, FR-MT-3, FR-MT-4, FR-MT-5,
SR-MT-2.

\end{enumerate}

\subsubsection{Knowledge Transfer Manager (S.2.7)}
