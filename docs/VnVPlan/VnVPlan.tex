\subsubsection{Webserver}
\paragraph{Communication Encryption}

\begin{enumerate}

\item{T-NFR-WS-2-1\\}

Type: Automatic
					
Initial State: Troitsky Toolbox webserver is active and able to receive packets.
					
Input/Condition: Packet is received.
					
Output/Result: Packet reject or negotiated.
					
How the test will be performed: Tools like Nmap or, Qualys SSL Labs, will scan the packet and observe the encryption protocol and cyphers. Only negotiate with packets that have secure and modern protocols (TLS 1.2 \& 1.3), reject older protocols (SSLv3, TLS 1.0, \& TLS 1.1) and weak cyphers (RC4, DES, or NULL) 
					
\item{T-NFR-WS-2-2\\}

Type: Automatic.
					
Initial State: Webserver is running and currently stable
					
Input/Condition: Updated system code
					
Output/Result: CI/CD test pass or fail
					
How the test will be performed: Scripts written to assert
\begin{enumerate}
  \item Requests to \texttt{http://...} results in a redirect to \texttt{https://...}
  \item Requests to \texttt{https://...} succeeds and returns a 200 OK
  \item A request using a deliberately downgrade TLS version throws a connection reset/SSL handshake error. 
\end{enumerate}
\item{T-NFR-WS-2-3\\}

Type: Dynamic

Initial State: Webserver is running and currently stable

Input/Condition: Webserver Address.

Output/Result: Potential vulnerabilities like broken or missing encryptions.

How test will be preformed: Using a tool like the Open Worldwide Application Security Project (OWASP) Zed Attack Proxy (ZAP) will actively probe a running web server to find vulnerabilities, including broken or missing encryption.
\end{enumerate}

\subsubsection{Toolbox Broker}
\paragraph{Extensibility and Overhead Management}
\begin{enumerate}
  \item T-NF-TB-1-1
  
  Type: Automatic / Manual 

  Initial State: The Toolbox Broker is running normally and successfully routing requests to existing, standard services. A new, isolated "mock" service has been created but is not yet known to the system.

  Input/Condition: The new mock service is registered with the Toolbox Broker

  Output/Result: \\
  \texttt{Pass:} Broker successfully routes the request to the new service and returns the response, with no older services function being compromised.\\
  \texttt{Fail:} Broker fails to find new service or existing services are broken by the addition of the mock service.

  How test will be preformed:
  \begin{enumerate}
    \item A script or test deploys a mock service
    \item The mock service is registered with the Broker at run time.
    \item A test request is sent to the new service to confirm it connects.
    \item A test request is sent to existing services to ensure backward compatibility and system stability remain intact.
  \end{enumerate}
  \item T-NF-TB-2-1
  
  Type: Automatic

  Initial State: The Toolbox Broker and a target services are running under normal system conditions.

  Input/Condition: A script sends a batch of requests directly to the target service to establish a baseline response time. Then it sends an identical batch of requests to the same service but routes them through the Toolbox Broker.

  Output/Results:\\
  \texttt{Pass:} The difference between the  baseline response time and the broker response time is strictly MAX\_BROKER\_OVERHEAD (100 ms) or less for all test requests.\\
  \texttt{Fail:} The presence of the broker delays the requests by more than 100ms
  How the test will be preformed:
  \begin{enumerate}
    \item An automate script sends 1000 requests directly to a test service and records the average response time
    \item The script sends 1000 identical requests through the toolbox broker to the same test service and records the average response time.
    \item The scrip then calculates $direct\_request\_time - broker\_request\_time$ for every request.
    \item The test pass if every calculation is below 100ms.
  \end{enumerate}
\end{enumerate}
\paragraph{Request Logging}
\begin{enumerate}
  \item T-NF-TB-3-1: 
  Type: Automatic

  Initial State:The Toolbox Broker is running, and its logging mechanism is accessible and at a known starting point.
  
  Input/Condition: A specific, authenticated user intentionally triggers two distinct actions through the Broker: one request that is known to succeed (e.g., fetching a public list) and one request that is known to fail (e.g., attempting an invalid or unauthorized operation)

  Output/Result: \\
  \texttt{Pass:} The Broker's log output displays two new distinct entries. Each entry explicitly contains: the user identifier, the operation requested, a timestamp, and a clear success/fail boolean or status code.\\
  \texttt{Fail:} No logs are generated, or the logs are missing one of the four required pieces of information (e.g., it logs the error but forgets to log who triggered it).

  How the test will be preformed:
  \begin{enumerate}
    \item A script authenticates the test user
    \item The script sends a valid and invalid request
    \item The script reads the brokers logs
    \item The script parses the most recent log entries and asserts that all four required fields (Member, Operation, Time, Success/Failure Status) are present and correctly recorded for both the successful and failed attempts.
  \end{enumerate}
\end{enumerate}
