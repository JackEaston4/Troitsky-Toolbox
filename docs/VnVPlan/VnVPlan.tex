\section{General Information}

\subsection{Summary}

The Troitsky Toolbox project seeks to create a centralized information repository and a collection of software
services that provide technical support for the McMaster Troitsky club. These services ensure information transfer 
between years and teams, and facilitate support and onboarding for new members. Served as a web application, 
accessible by all current club members, the services provided will simplify the technical components of the bridge 
design process, decreasing the barrier to becoming a competitive team. 

One of the primary services in the toolbox is the model analysis service, which allows teams to load STEP files of their bridge 
designs and perform basic analysis on the models. This service will provide teams with a simplified analysis of their design, when compared to 
external static model analysis software, and will integrate with the material testing component and the rule compliance checker to provide a more specified analysis given the 
build material properties and current competition rules. Services regarding the information repository will include the ability to search through past designs and load them into 
the model analysis service, allowing teams to upload their designs with exit documentation and providing customized material testing result upload features. A knowledge transfer 
service collects executive handoff documents so that club knowledge carries over between years.
In managing the toolbox access, role-based access control (RBAC) will be integrated to ensure that information is kept within the club, limiting access, and allowing executive members 
the ability to manage club users.

\subsection{Objectives}

The primary objective of the verification and validation plan is to outline the approach to ensure that the Troitsky Toolbox 
project will meet the requirements outlined in the software requirements specification. This plan will help to build 
confidence in the correctness, reliability and safety of the system, focusing verification on high-risk points and safety-critical concerns 
outlined in the hazard analysis.

The V\&V plan will primarily focus on these system objectives outlined below. There are also goals outlined that have been deemed 
out of scope for the current development cycle, but will be outlined in documentation as goals for future year development.

\subsubsection{Primary Objectives}
\begin{itemize}

  \item \textbf{Adequate model analysis correctness:} Testing the correctness of the model analysis service is vital to the usability of the toolbox, as, without 
  ensured correctness, teams will not be able to rely on the results. These results will not only be used by teams in the bridge design process, but will also 
  guide them in making estimates of their bridge's weight and ultimate load capacity.
  
  \item \textbf{Data integrity and persistence:} The system must ensure data integrity and security in the knowledge repository. The repository will 
  serve as the club's main data storage and information transfer, so losing data would be a critical concern and would defeat the project's purpose.
  
  \item \textbf{Access control:} The RBAC in the club will maintain data privacy both between teams and outside of the club. Testing 
  this access control will provide confidence to teams when storing current bridge designs in the system, and ensure that executive and exit documentation is private to the club. 
  
  \item \textbf{Demonstrating functional usability:} The functional usability of the system determines if it will be fully integrated into the club's organization and 
  individual McMaster teams' bridge design and development process.
   
\end{itemize}

\subsubsection{Out-of-Scope Objectives}
\begin{itemize}
  
  \item \textbf{Industry standard static model analysis performance:} The model analysis service is intentionally designed to provide a simplified approximation of static model 
  analysis, so its accuracy will have a larger tolerance than industry-standard tools and will not aim to match established services.

  \item \textbf{Full year competition testing:} The toolbox testing will not include an end-to-end full-year competition evaluation within the current development cycle. This would require a usable product 
  from the beginning of the school term, allowing teams to use the service throughout their full design process.
\end{itemize}

\subsubsection{Assumptions}
There is an assumption of the correctness of external libraries (BFE.NET, IxMilia.Step, occt-import-js, three.js,
SQL Server) used. It is assumed that they are verified by their maintainers; only our
integration with them is tested.

\subsection{Custom Documents}

\subsubsection{Fall - Interviews}

The primary CD for the fall term development is interviews conducted with core stakeholders: experienced Troitsky club members and executives. These semi-structured interviews will 
help outline expectations and prioritization of services from knowledgeable members. These interviews will be anonymized to ensure user privacy and aggregated into usable results for the 
toolbox development process. The interviews will be vital in checking any assumptions made in the SRS with experienced club members.

In addition to the core interviews for the fall CD, a survey has been performed to begin the requirements elicitation process. The \href{https://github.com/JackEaston4/Troitsky-Toolbox/blob/main/docs/CDs/Interviews/SurveyDesign.md}{survey design record} and \href{https://github.com/JackEaston4/Troitsky-Toolbox/blob/main/docs/CDs/Interviews/Troitsky%20Toolbox%20%E2%80%94%20Member%20Needs%20%26%20Service%20Priority%20Survey.csv}{raw data} are stored in the project repository, and the results were used in the SRS \citep{TroitskySRS} to 
outline the priority of services and core issues members are currently facing.

\subsubsection{Winter - Usability Report}

The CD completed in the winter term will be a usability report, allowing for a more complete assessment of the functional usability of the toolbox. 
This round of testing will be performed with a more complete iteration of the product, allowing for more complete analysis of different system services' usability. 
Users will be gathered spanning different experience levels, both in club experience and technical experience (modelling), creating valuable data about the system's performance. 
Specific user functions will be tested, with tasks that follow the G.5 usage scenarios, measured by completion rate and time on task.

This CD will further strengthen the V\&V of the system, ensuring that complete functional and non-functional requirements come together into a fully usable service.

\subsection{Tests for Functional Requirements} \label{SecFRTests}

The tests below are categorized by the components defined in Section S.2 of the
SRS \citep{TroitskySRS}, so that every functional requirement is covered. Each
test is a system-level test of the deployed system, following a workflow that a
club member performs through the Toolbox Web App, and verifies several related
requirements. The tests also verify the functional safety and security
requirements that the Hazard Analysis Roadmap \citep{TroitskyHazardAnalysis}
plans for the capstone. Together, they verify the model analysis correctness,
data integrity, and access control identified as primary objectives in the
Objectives section, while functional usability is assessed by the non-functional
tests and the winter usability report.

Inputs and expected outputs refer to the symbolic constants of
Table~\ref{TblSymbolicConstants} and the test data of Table~\ref{TblTestData}
(Symbolic Parameters appendix), shown in \textsc{small capitals}. Tests whose
outputs are numerical or follow from a formula are automated, so that they can be
repeated on every change; tests that depend on what a member sees on screen are
manual.

\subsubsection{Web Server (S.2.1)}

\begin{enumerate}

\item \testdef{T.FR.WS.1.1}\\
\textbf{Control:} Manual\\
\textbf{Initial State:} System deployed. User not logged in.\\
\textbf{Input:} User opens the public landing page, then attempts to open the
Knowledge Repository. User then logs in with valid credentials, opens the
Knowledge Repository, and logs out.\\
\textbf{Output:} The landing page is shown without logging in. The Knowledge
Repository redirects to the login page until the user logs in, and is no longer
accessible after logout.\\
\textbf{Derivation:} Verifies FR-WS-1, FR-WS-2, FR-WS-3.

\end{enumerate}

\subsubsection{Access Control System (S.2.2)}

\begin{enumerate}

\item \testdef{T.FR.AC.2.1}\\
\textbf{Control:} Manual\\
\textbf{Initial State:} An executive is logged in.\\
\textbf{Input:} The executive creates an account three times: with a password
one character shorter than \const{password\_min\_length}, with an entry from
\const{password\_blocklist}, and with a password consisting solely of lowercase letters and exactly \const{password\_max\_length} characters long. The executive then changes the
account's role and team, ends its session from the server side, and deactivates
it.\\
\textbf{Output:} The first two passwords are rejected, with a message stating
that the password is too short or too common. The third is accepted, since no
composition rules apply. The account always has exactly one role and at most one
team. Ending the session logs the user out, and the deactivated account cannot
log in.\\
\textbf{Derivation:} Verifies FR-AC-1, FR-AC-2, FR-AC-4, FR-AC-5, SR-AC-2,
SR-WS-5.

\item \testdef{T.FR.AC.2.2}\\
\textbf{Control:} Automatic\\
\textbf{Initial State:} One account for each role of FR-AC-2, on two different
teams. Each team has a current bridge model.\\
\textbf{Input:} A script requests, as each account, member management, team
assignment, rule configuration, season archiving, test result review, and each
team's current model.\\
\textbf{Output:} Member management, team assignment, and rule configuration are
allowed only for executives and maintainers; season archiving and test result
review only for executives; and a team's current model only for members of that
team. Every other request is refused with an error and changes nothing.\\
\textbf{Derivation:} Verifies FR-AC-3, FR-AC-6, FR-BR-2.

\end{enumerate}

\subsubsection{Toolbox Broker (S.2.3)}

\begin{enumerate}

\item \testdef{T.FR.BR.3.1}\\
\textbf{Control:} Manual\\
\textbf{Initial State:} System has just been started. User logged in.\\
\textbf{Input:} User opens each tool. The Material Testing Manager is then
stopped, and the user requests it, then searches the Knowledge Repository.\\
\textbf{Output:} Every tool opens. The request to the stopped service returns an
error message within \const{broker\_timeout} instead of hanging, and the search

\textbf{Derivation:} Verifies FR-BR-1, FR-BR-3, FR-BR-4.

\end{enumerate}

\subsubsection{Knowledge Repository (S.2.4)}

\begin{enumerate}

\item \testdef{T.FR.KR.4.1}\\
\textbf{Control:} Manual\\
\textbf{Initial State:} User logged in. Repository contains items with known
metadata.\\
\textbf{Input:} User uploads one file of each type in \const{common\_file\_types},
each with a title, a category from \const{category\_list}, a year, a team, and
tags. User then makes three uploads that each break one metadata rule: no title,
a category not in \const{category\_list}, and no year. Finally, the user searches
by keyword, filters by category, year, team, and tag, previews a file of each
type in \const{preview\_file\_types}, and downloads every uploaded file.\\
\textbf{Output:} Valid uploads are stored with their metadata. Each of the three
invalid uploads is rejected, with a message naming the field. Searches and
filters return exactly the items that match them, previews display in the
browser, and each downloaded file has the same SHA-256 hash as the uploaded
file.\\
\textbf{Derivation:} Verifies FR-KR-1, FR-KR-2, FR-KR-3, FR-KR-4, SR-KR-4.

\item \testdef{T.FR.KR.4.2}\\
\textbf{Control:} Manual\\
\textbf{Initial State:} A member has uploaded an item.\\

\subsubsection{Bridge Failure Module}

\wss{Include a blurb here to explain why the subsections below cover the module.

This module determines whether a bridge fails, i.e., whether there is an element in the bridge whose
factor of safety is less than one. The examples below are illustrative of the test types, in reality
there will be several for each type.

\begin{enumerate}

\item{Artificial, Bridge Succeeds\\}

Type: Automatic
					
Initial State: System requests artificial data for an STEP model to analyze.
					
Input: This bridge contains two elements. Element $e_a$ is of a material $m_a$ where $\mu_{strength}(m_a) = 5$ and 
$\sigma_{API}(e_a) = 4 $ and Element $e_b$ is of a material $m_b$ where $\mu_{strength}(m_b) = 3$ and 
$\sigma_{API}(e_b) = 2 $.
					
Output: $BridgeFailure \equiv false$

Test Case Derivation: \wss{Justify the expected value given in the Output field}

\begin{align*}
BridgeFailure &\equiv (\exists e: \frac{\mu_{\text{strength}}(\text{elementMaterial}(e))}{\sigma_{\text{API}}(e)} < 1) \\
              &\equiv \frac{\mu_{\text{strength}}(\text{elementMaterial}(e_a))}{\sigma_{\text{API}}(e_a)} < 1 \; \lor \; \frac{\mu_{\text{strength}}(\text{elementMaterial}(e_b))}{\sigma_{\text{API}}(e_b)} < 1 \\
              &\equiv \frac{5}{4} < 1 \; \lor \; \frac{3}{2} < 1 \\
              &\equiv \text{false} \lor \text{false} \\
              &\equiv \text{false}
\end{align*}

How test will be performed: Through MsTest within the .NET solution used for implementation

Type: Automatic

$\sigma_{API}(e_a) = 4 $ and Element $e_b$ is of a material $m_b$ where $\mu_{strength}(m_b) = 3$ and 
$\sigma_{API}(e_b) = 4 $.
					
Output: $BridgeFailure \equiv true$

Test Case Derivation: \wss{Justify the expected value given in the Output field}

\begin{align*}

\subsubsection{Rules Compliance Module}

\wss{Include a blurb here to explain why the subsections below cover the module.

This module determines whether a bridge complies with the rules for the Troitsky competition.
Because the competition rules change each year, the fields denoting rule-based constraints are variable so they
can be easily updated. 
The examples below are illustrative of the test types, in reality
there will be several for each type.

For brevity, the example rules are the same in all three test cases.
The maximum weight is $7$ kg, the minimum length is $175$ m, the maximum length is $225$ m, 
the minimum width is $45$ m, the maximum width is $60$ m and the minimum clearance height is
$45$ m. Furthermore, let an $iB$ (in bounds) function be defined as

\[
  iB(val, lower, upper) \equiv lower \le val \land val \le upper
\]

Lastly, variables shall be in the form of $qualQty$ where $qual \in \text{(val, min, max)}$ and 
$Qty \in \text{(Wt, Ln, Wd, Ht)}$. The variable shall be understood as "the $qual$ for the $Qty$".
The items in the $qual$ (qualifiers) set are short for value, minimum and maximum respectively,
while the items in the $Qty$ (quantities) set are short for weight, length, width and height respectively.
If no qualifier is there (e.g. $Ln$), an implicit qualifier of $val$ shall be assumed.

\begin{enumerate}

\item{Artificial, Rules Compliant\\}

Type: Automatic
					
Initial State: System requests artificial data for an STEP model to analyze.
					
Input: This bridge weighs $5$ kg, has a length of $200$ m, a width of $50$ m and a clearance height of $50$ m. 
					
Output: $isValid \equiv true$

Test Case Derivation: \wss{Justify the expected value given in the Output field}

\begin{align*}
isValid &\equiv iB(Wt, 0, maxWt) \land iB(Ln, minLn, maxLn) \; \land \\ 
        & \qquad iB(Wd, minWd, maxWd) \land Ht < maxHt \\
        &\equiv iB(5, 0, 7) \land iB(175, 200, 225) \land iB(45, 50, 60) \land 45 \le 50 \\
        &\equiv true \land true \land true \land true \\
        &\equiv true \\
\end{align*}

How test will be performed: Through MsTest within the .NET solution used for implementation

\item{Artificial, Rules Non-Compliant\\}

Type: Automatic
					
Initial State: System requests artificial data for an STEP model to analyze.
					
Input: This bridge weighs $5$ kg, has a length of $200$ m, a width of $61$ m and a clearance height of $50$ m. 
					
Output: $isValid \equiv false$

Test Case Derivation: \wss{Justify the expected value given in the Output field}

\begin{align*}
isValid &\equiv iB(Wt, 0, maxWt) \land iB(Ln, minLn, maxLn) \; \land \\ 
        & \qquad iB(Wd, minWd, maxWd) \land Ht < maxHt \\
        &\equiv iB(5, 0, 7) \land iB(175, 200, 225) \land iB(45, 61, 60) \land 45 \le 50 \\
        &\equiv true \land true \land false \land true \\
        &\equiv false \\
\end{align*}

How test will be performed: Through MsTest within the .NET solution used for implementation
					
\item{Natural}

Type: Automatic
					
Initial State: System requests an STEP file that models a bridge
					
Input: The STEP file
					
Output: If,
\[iB(Wt, 0, maxWt) \land iB(Ln, minLn, maxLn) \land iB(Wd, minWd, maxWd) \land Ht < maxHt \]
$isValid \equiv true$. Otherwise, $isValid \equiv false$.

Test Case Derivation: From the formalization in (S.7.2 (2)). The external CAD library will return
the bridge's weight, length width and height. Then, this module will have gained its input to perform its calculations

through a form. Once the user submits it, the system adds it to the knowledge repository.

Automatic tests are a poor fit here because the bulk of the work is to convert user-entered text into a format the 
database uses, not re-confirming the abilities of a highly reliable industry-standard database. Thus, manual
tests shall be used.

  \item The user fills out the form and submits it

  \item The system uploads the document to the knowledge repository.
  \item Once recieving a confirmation of success, it displays a "form successfully submitted" message to the user
\end{itemize}

How test will be performed: Manually, through the front end. 
    
\end{enumerate}
