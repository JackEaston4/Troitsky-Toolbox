\section{Introduction}

\subsection{Background}

The Troitsky Toolbox is a web-based application that supports the McMaster
Troitsky club, a student organization whose teams design, analyze, and build
bridges out of popsicle sticks, white glue, and dental floss for the annual
Troitsky Bridge Building Competition. The Toolbox centralizes the club's
knowledge, including past designs, material testing data, and exit documents,
and provides technical tools that allow teams to visualize their bridge models,
estimate their performance, and check them against the competition rules. The
problem and goals of the project are described in more detail in the Problem
Statement and Goals document, and the system itself is specified in the
Software Requirements Specification (SRS).

\subsection{Hazard Definition}

A hazard is defined as ``a system state or set of conditions that, together
with a particular set of worst-case environmental conditions, will lead to a
loss'' \cite[p.~17]{LevesonAndThomas2018}. For the Troitsky Toolbox, a hazard is therefore any
condition of the system that, combined with how members use it, could lead to
the loss of club knowledge, the disclosure or corruption of club data, the
disruption of club activities, or members acting on incorrect information.

The Toolbox does not control any physical equipment, so the hazards it presents
are primarily to the club's data and decisions rather than to people. The one
exception is indirect: the Performance Analysis System produces estimates of a
bridge's failure load, and a team that trusts an incorrect estimate may build or
load test a bridge on that basis. This harm would be seen primarily in competition results, 
depending on the accuracy of the estimates. This document identifies these hazards, the
failure modes that cause them, and the safety and security requirements that
mitigate them.

\section{Scope and Purpose of Hazard Analysis}

The purpose of this hazard analysis is to identify the ways in which the
Troitsky Toolbox could fail or be misused, assess their effects on the club and
its members, and derive requirements that prevent or mitigate them. The
resulting safety and security requirements are outlined in
Section~\ref{SecSafetyReqs}, and Section~\ref{SecRoadmap} states which of them
will be implemented during the capstone, so that they are designed, implemented, 
and verified alongside the rest of the system.

The losses that could result from the hazards identified in this document are:

\begin{itemize}
    \item \textbf{Loss of club knowledge:} Designs, test data, or exit documents
    are deleted, corrupted, or never captured, so that the knowledge the Toolbox
    exists to preserve is lost when members graduate. As the Toolbox becomes the
    club's central repository, a single failure can affect several years of
    accumulated information.
    \item \textbf{Loss of data integrity:} Stored data, such as material test
    results or competition rules, is incorrect or inconsistent, so that the
    results of the analysis tools are wrong.
    \item \textbf{Misleading analysis results:} A team relies on an incorrect
    performance estimate or compliance result, leading to a weaker bridge, a
    bridge that is disqualified for violating a competition rule, or wasted
    build time and materials.
    \item \textbf{Loss of confidentiality:} Members' personal information or the
    club's unpublished designs are disclosed to unauthorized users, including
    competing universities.
    \item \textbf{Loss of availability:} The Toolbox, or one of its tools, is
    unavailable when members need it, such as in the weeks leading up to the
    competition.
    \item \textbf{Loss of trust:} Repeated failures lead members to stop using
    the Toolbox and return to scattered, undocumented information sharing,
    defeating the purpose of the project.
\end{itemize}

The analysis covers every software component of the Toolbox listed in
Section~\ref{SecBoundaries}, the interfaces between the Toolbox and the
external components it depends on, and the processes used to develop, deploy,
and maintain the Toolbox, including its handover to future software subteam
members. The following are outside the scope of this analysis:

\begin{itemize}
    \item The physical construction and load testing of bridges, including the
    safety procedures followed by the club during testing.
    \item The CAD software that teams use to create their bridge models.
    \item The Troitsky Bridge Building Competition itself, including its rules
    and judging.
    \item Failures of the hosting infrastructure's physical hardware, beyond
    their effect on the availability and durability of the Toolbox's data.
\end{itemize}

\section{System Boundaries and Components} \label{SecBoundaries}

The Troitsky Toolbox is structured around a central broker: each tool, as well
as the shared data storage, is a service that registers with the broker, and all
communication between services passes through it. The components below are
those described in Section S.1 of the SRS, and are shown in
Figure~\ref{FigComponents}. The requirements each component is responsible for
are listed in Section S.2 of the SRS, using the prefixes given below.

\subsection{Inside the System Boundary}

The following components are developed by the team and are within the system's
control and responsibility:

\begin{itemize}
    \item \textbf{Web Server (WS):} Serves the Toolbox Web App and the public
    landing page, handles member login, and forwards requests for club services
    to the Toolbox Broker.
    \item \textbf{Access Control System (AC):} Manages member accounts and
    roles, authenticates members, and decides which services and data each role
    may access.
    \item \textbf{Toolbox Broker (BR):} Registers services, verifies every
    request with the Access Control System, and routes it to the service that
    provides the requested operation. Because all communication passes through
    the broker, a failure of the broker affects every tool.
    \item \textbf{Knowledge Repository (KR):} Stores all club information,
    including documents, bridge models, material test results, competition
    rules, and handoff documents, and allows members to search and contribute to it.
    \item \textbf{Model Analysis System (MA):} Imports bridge models in the STEP
    format, renders them in 3D, and extracts the bridge properties needed for
    analysis, such as its dimensions and mass.
    \begin{itemize}
        \item \textbf{Performance Analysis System (PA):} Estimates the failure
        load and load-to-mass ratio of a bridge model, using the extracted model
        data and the material properties provided by the Material Testing
        Manager.
        \item \textbf{Rule Compliance System (RC):} Checks a bridge model against
        the competition rules configured by club members.
    \end{itemize}
    \item \textbf{Material Testing Manager (MT):} Imports and stores material
    test results from CSV and Excel files, compares them against previous years,
    and derives the material properties used by the Performance Analysis System.
    \item \textbf{Knowledge Transfer Manager (KT):} Collects exit documents and
    role records from executives and team leads, and stores them in the
    Knowledge Repository.
\end{itemize}

\subsection{Outside the System Boundary}

The following entities interact with the system, but are not under its direct
control:

\begin{itemize}
    \item \textbf{Club members:} The general members, executives, and software
    subteam maintainers who use the Toolbox. Their decisions, including how they
    act on the results of the analysis tools, are outside the system's control.
    \item \textbf{CAD software and STEP files:} The software teams use to design
    their bridges, and the STEP files it exports. The Toolbox receives these
    files but does not control how they are created.
    \item \textbf{CAD/geometry library:} The external library used by the Model
    Analysis System to read STEP files.
    \item \textbf{Static model analysis services:} The external libraries or APIs used to perform
    the static model analysis of bridge model STEP files (SRS E.2).
    \item \textbf{Material test data files:} The CSV and Excel files produced by
    members during material testing, whose content depends on how the tests
    were performed and recorded.
    \item \textbf{Competition rules:} The official rules published by the
    competition organizers, which change from year to year and must be
    configured into the Rule Compliance System by members.
    \item \textbf{Hosting infrastructure:} The server, operating system, database
    server, and network on which the Toolbox is deployed.
    \item \textbf{Web browsers:} The browsers through which members access the
    Toolbox Web App.
\end{itemize}

\section{Critical Assumptions}

The following assumptions are made about the system and its environment. Each
assumption states the class of hazards it removes from the scope of this
analysis. Assumptions have been kept to a minimum, and failures that the system
can reasonably detect or mitigate, such as invalid input files, service
outages, and data entry errors, remain within the scope of the analysis.

\begin{enumerate}
    \item \textbf{Analysis results are advisory:} Members treat the results of
    the Performance Analysis and Rule Compliance Systems as guidance, and the
    club verifies the final design against the official competition rules and
    follows its own safety procedures when load testing bridges. This assumption
    removes physical injury during bridge testing from the scope of this
    analysis. Hazards caused by incorrect or misleading results, and by results
    being presented in a way that encourages over-reliance, remain in scope.

    \item \textbf{Members act in good faith:} Authenticated members do not
    intentionally misuse their access, for example by deliberately deleting or
    falsifying club data. This assumption removes deliberate insider sabotage
    from the scope of this analysis. Accidental misuse by members, and attacks
    by people outside the club, remain in scope.

    \item \textbf{STEP files reflect the intended design:} The STEP files that
    teams upload accurately represent the bridge they intend to build. This
    assumption removes differences between a team's CAD model and its physical
    bridge from the scope of this analysis. Files that are invalid, corrupted, or
    that cannot be read remain in scope.

    \item \textbf{The CAD/geometry library is correct:} The external library used
    by the Model Analysis System correctly reads the geometry of valid STEP
    files. This assumption removes defects within the library itself from the
    scope of this analysis. Errors in how the Toolbox uses the library's output
    remain in scope.

    \item \textbf{Test data reflects the tests performed:} The material test
    results that members import were measured using the club's testing
    procedure. This assumption removes errors in the physical testing process
    from the scope of this analysis. Data entry errors, malformed files, and
    physically impossible values remain in scope.

    \item \textbf{Hosting infrastructure is maintained:} The server, operating
    system, and database server on which the Toolbox is deployed are kept
    updated and secured by whoever hosts them. This assumption removes
    vulnerabilities within the hosting platform itself from the scope of this
    analysis. Outages of the hosting infrastructure, and their effect on the
    availability and durability of the Toolbox's data, remain in scope.
\end{enumerate}

\section{Safety and Security Requirements} \label{SecSafetyReqs}


\subsection{Functional Requirements}

\begin{itemize}
    \item \textbf{SR-AC-2:} The Access Control System shall require passwords to meet the length and
    blocklist requirements of NIST SP 800-63B-4 for single-factor authentication \cite{NIST80063B4},
    and shall not impose composition rules. [H-AC-2]
    \item \textbf{SR-WS-5:} The Web Server shall allow a member's session to be ended from the server side. [H-WS-6]
    \item \textbf{SR-KR-2:} The Knowledge Repository shall always prompt the user
    to confirm an action that will result in deletion or modification of stored files. [H-KR-2]
    \item \textbf{SR-KR-3:} The Knowledge Repository shall require that uploads of 
    current competition year files are uploaded with a current team, limiting file access 
    to only members of that team and executives. [H-KR-3]
    \item \textbf{SR-KR-4:} The Knowledge Repository shall reject an upload that
    does not include a title, a category selected from a standardized list, and a year. [H-KR-4]
    \item \textbf{SR-KR-5:} The Knowledge Repository shall return an error message 
    whenever an uploaded file cannot be stored or a data retrieval error occurs. [H-KR-5]
    \item \textbf{SR-MA-1:} The Model Analysis System shall display a summary of inputted models
    to allow users to confirm the details and ensure accuracy and correctness. [H-MA-1]
    \item \textbf{SR-MA-2:} The Model Analysis System shall display the units of the inputted models, 
    along with a scale reference in the 3D view. [H-MA-2]
    \item \textbf{SR-MA-3:} The Model Analysis System shall stop processing a
    model that has not finished within MA\_TIMEOUT, and shall tell the member why
    processing stopped. [H-MA-3]
    \item \textbf{SR-PA-1:} The Performance Analysis System shall display an
    error message whenever the calculation service fails, does not respond, or returns an inappropriate 
    value. [H-PA-1]
    \item \textbf{SR-RC-1:} The Rule Compliance System shall display the competition year 
    of the active rules with each result, and shall indicate when 
    manual verification is required. [H-RC-1]
    \item \textbf{SR-KT-1:} The KT shall enforce schema-level validation on all handoff submissions, rejecting any submission that leaves mandatory operational fields blank or below a minimum character threshold. [H-KT-1]
    \item \textbf{SR-KT-2:} The KT shall verify that all cross-referenced bridge models, test result IDs, and rule versions stored in the Knowledge Repository exist and are valid before a handoff document is accepted. [H-KT-2]
    \item \textbf{SR-KT-3:} The KT shall track role succession states and block the archival of an outgoing lead's account until a designated successor or faculty advisor has been assigned to inherit the role records. [H-KT-4]
    \item \textbf{SR-KT-4:} The KT shall enforce a three-stage publishing lifecycle (Draft \(\rightarrow\) Review \(\rightarrow\) Publishing). [H-KT-1, H-KT-3, H-KT-5]
    \item \textbf{SR-KT-5:} The KT shall verify that the KR sends an acknowledgement when documents are published, confirming that they were saved. [H-KT-6]
    \item \textbf{SR-MT-1:} The MT shall automatically parse, validate, and convert all uploaded data into standardized base units, rejecting datasets lacking unit metadata. [H-MT-2]
    \item \textbf{SR-MT-2:} The MT shall mandate the inclusion of grain orientation data on any wooden material test. [H-MT-3]
    \item \textbf{SR-MT-3:} The MT shall perform automated sanity checks to ensure all submitted data is within acceptable boundaries. [H-MT-1]
    \item \textbf{SR-SYS-1:} The project build system shall strictly enforce deterministic dependency resolution by pinning all direct and transitive third-party dependencies to immutable versions using lockfiles. [H-SYS-1]
    \item \textbf{SR-SYS-2:} The deployment pipeline shall enforce mandatory branch protection rules that block deployment to production environments until all automated unit tests pass in the CI/CD pipeline, and every code change has been reviewed and documented. [H-SYS-2]
    \item \textbf{SR-SYS-3:} The system shall provide fully containerized, reproducible deployment configurations (e.g., Dockerfile and docker-compose.yml) alongside automated setup scripts, standardized API documentation (e.g., OpenAPI/Swagger), and a maintainer onboarding guide that allows a new developer to build, deploy, and verify the full system locally within a single documented procedure. [H-SYS-3]
    
\end{itemize}

\subsection{Non-Functional Requirements}

    \item \textbf{SR-WS-2:} The previous production code of the application shall be stored on the server so

    \item \textbf{SR-WS-3:} All actions in the code shall be thread-safe, unless it is impossible for two

    \item \textbf{SR-WS-4:} The server shall be hosted in a location with a robust internet connection that is
    available at least 99.9\% of the time, the residential standard. [H-WS-4]

    \item \textbf{SR-KR-1:} Backups of the Knowledge Repository shall be stored on an external platform. [H-KR-1]
    
\end{itemize}
